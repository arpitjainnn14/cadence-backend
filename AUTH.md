# Auth design notes

**Why argon2.** Passwords are hashed with argon2id (via `pwdlib`). It is memory-hard, so a stolen database is expensive to brute-force on GPUs, unlike fast hashes such as SHA-256. Each hash embeds its own random salt and parameters, so they can be raised later without a schema change.

**Why httpOnly cookies, not localStorage.** Anything in localStorage is readable by any script on the page, so one XSS bug leaks the session. An httpOnly cookie is invisible to JavaScript; the browser attaches it itself. Tokens never appear in response bodies. The price is CSRF exposure, handled with `SameSite=Lax`, a separate JS-readable `csrf_token` cookie, and `Secure` in production.

**Why short access plus long refresh.** The access JWT lives 15 minutes and is verified without a database lookup, so a leaked one is useful only briefly. The refresh token lives 30 days, is opaque, and is stored (as a sha256 hash) server-side, so it can be revoked. The user stays signed in without a long-lived bearer credential on every request. The access cookie is scoped to `/api` and the refresh cookie to `/api/auth`, so the long-lived token is sent only where it is needed.

**Rotation and reuse detection.** Every refresh retires the presented token and issues a new one in the same family. A retired token should never come back. If one does (after the grace window), someone has a copy, either the attacker or the real user after theft, so the whole family is revoked and everyone must log in again. That revocation is committed even though the response is a 401 (the router returns the response instead of raising, because `get_db` rolls back on exceptions).

**The 10 second grace.** Two browser tabs can fire a refresh at the same moment with the same cookie; the loser would present an already-rotated token. If a retired token is replayed within 10 seconds of its rotation, the request gets a 401 but the family is left alone, so the winner's new token keeps working. Rows are locked (`SELECT ... FOR UPDATE`) so truly concurrent rotations serialise.

**Pinning the algorithm.** Decoding passes `algorithms=["HS256"]` explicitly and requires the claims `sub, exp, iat, jti, type`, with `type == "access"`. Letting the token's own header pick the algorithm enables the classic `alg: none` and key-confusion attacks, and the `type` check stops a refresh-style token from being used as an access token.

**One error message.** Login answers `Invalid email or password` for both a wrong password and an unknown email, and hashes a dummy password for unknown emails, so neither the response nor its timing reveals which accounts exist.

**Server-side logout.** Clearing cookies only affects the browser that did it. Logout also revokes the refresh token in the database, so a copied refresh cookie stops working immediately. The access JWT is stateless and stays valid until it expires (at most 15 minutes); that is the deliberate trade-off for not hitting the database on every request.

**Why CSRF double-submit on top of SameSite=Lax.** Cookies are attached by the browser automatically, so another site can make the browser send a state-changing request with our session cookies. `SameSite=Lax` blocks most of that, but it is one defence relying on browser behaviour (and on same-site subdomains being trusted). Double-submit adds a second, independent check: at login we set a random `csrf_token` cookie that JavaScript can read, and the SPA must copy it into an `X-CSRF-Token` header on every `POST/PUT/PATCH/DELETE`. A foreign site can make the browser send the cookie but cannot read it, so it cannot produce the matching header. The middleware compares them with `hmac.compare_digest` and answers 403 on any mismatch or missing value. Login is exempt (there is no session to hijack yet), as is `/api/internal/*`, which is authenticated by a shared secret rather than cookies. The token is not bound to the session server-side; that is acceptable here because an attacker who can plant cookies on our domain already has bigger powers than CSRF.

**Why rate-limit logins, per email and per IP.** The single user's password is the only thing between the internet and the data, and argon2 only slows guessing, it does not stop it. After 5 failed attempts in 15 minutes for an email, or from an IP, further logins get 429 before the password is even checked. Two keys cover two attacks: the per-email limit stops many guesses against the one real account from many IPs; the per-IP limit stops one machine trying many emails. Behind Vercel and Cloud Run the client IP comes from `X-Forwarded-For`, which a client can forge, so the per-IP limit is best-effort and the per-email limit is the one an attacker cannot dodge. The flip side is that someone can lock the owner out by failing on purpose; the lockout expires on its own after 15 minutes, which is the accepted trade-off for a single-user app. Attempts are stored in the database (not in memory) so the limit survives restarts and works across Cloud Run instances. The login handler returns its 401/429 instead of raising, because `get_db` rolls back on exceptions and the failed attempt must be committed to count.

**Why commit before the response.** FastAPI's default dependency scope runs the rest of `get_db` (the commit) after the response has been sent. A client could then receive a 200 for something not yet committed, and a failing commit could not become an error response. `DbSession` declares the dependency with `scope="function"`, so the commit happens when the endpoint returns, before the response goes out.

**Why the repository pattern.** All SQL lives in each feature's `repository.py`; services hold the rules (lockout policy, token rotation) and take repositories as arguments; routers only wire HTTP to services. That buys three things. Testability: policy code like `is_locked` and token rotation can be tested against a small interface, and each repository's queries get their own direct tests. Swappable storage: moving a table, adding caching or changing a query touches one file, not every route. Thin routers: a route reads as a short sequence of business steps, and there is exactly one place to look for any query. Repositories never commit; the request-scoped session from `get_db` is the unit of work, so a request's writes succeed or fail together.
